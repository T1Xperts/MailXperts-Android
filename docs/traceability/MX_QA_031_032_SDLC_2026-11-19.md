Current implemented trust boundary is **on device only**, with event-code allowlisting and no network upload. Android private files use OS file-based protection and app backup is disabled; the branch does not add a separate Android Keystore encryption layer for diagnostics. Threat-model review required.

## LLD-MX-QA-032 (candidate implementation)
- \`DiagnosticSanitizer.java\`: allowlisted event/area codes, exception *class only*, up to eight own-package method/line frames, with no exception message or external frames.
- \`DiagnosticLogger.java\`: installs uncaught-exception handler, delegates to original handler, collects supported \`ApplicationExitInfo\` reason indicators on API 30+, writes bounded reports to \`getNoBackupFilesDir()\`, rotates to one old report, exposes export/clear helpers.
- \`DiagnosticsActivity.java\`: manual Android document export, local history refresh/delete with confirmation, explicit banner that automated GitHub sync is NOT ACTIVE.
- \`MailXpertsApplication.java\`: installs reporting after application context initialization.
- \`MessageActivity.java\`: safe Reply / Reply All / Forward tapped breadcrumbs, without message metadata.
- \`ComposeActivity.java\`: composer-created, HTML editor-ready and 15-second timeout events; timeout is not proof of a process crash.
- \`Navigation.java\`, \`SettingsActivity.java\`, \`AndroidManifest.xml\`: discoverable diagnostics screen and internal activity registration.
- \`DiagnosticSanitizerTest.java\`, \`DiagnosticsIntegrationContractTest.java\`: new local source/test code; test execution evidence **not yet confirmed**.

## LLD-MX-QA-032-GATEWAY (not implemented)
1. Separate authenticated diagnostic intake service; require user/session identity, app attestation as appropriate, validated consent and scoped per-tenant authorization. No secret in APK.
2. Queue only redacted bounded schemas; enforce retention/deletion/abuse controls, payload size caps and rate limits. Never accept arbitrary logcat, source mail, user attachments or free-text stacktrace.
3. Use a server-side GitHub App installation with minimal \`Issues:write\` to a **private** issue repository. Note current \`T1Xperts/MailXperts-Android\` repository is public and should **not** receive raw incident details. Private issue storage location must be designated by the Product Owner/security lead.
4. Deduplicate by server-derived fingerprint and update existing incident counters and version ranges; do not create an issue storm.
5. Support user opt-in/out and queued offline retry with no auto-action beyond diagnostic issue reporting. Human approval still needed before code, deploy, email or financial actions.
6. External dependencies: production diagnostic hostname/HTTPS, identity and consent service, secrets vault, GitHub App installation, threat model/privacy approval. These are pending.
