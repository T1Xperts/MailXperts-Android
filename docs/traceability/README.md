## Evidence legend and hard rules

- **Source requirement**: original issue #3 for MX-QA, #29 for AI and detailed Odoo story #31.
- **HLD ID**: architecture outline in companion catalogue, **not an approved design artifact**. Existing standalone architecture documents are listed below.
- **LLD ID**: an as-built code/component association where code exists, otherwise a **proposed design**, not a completed low-level specification.
- **Code**: a clickable file path verified on `main` or exactly listed among changed files in draft PR #27/#30. An existing class does not alone prove the entire acceptance criteria are met.
- **Test case ID**: newly proposed planned `TC-<requirement>-01` marker; **not previously executed**. Test-file links refer to existing class-level automated assets, not a proven case-by-case execution map.
- **Results and QA**: aggregated workflow passes, owner acceptance and missing device/provider acceptance are separate. Never infer individual testcase PASS from a green pipeline.
- **Release version**: source/PR feature association or candidate, **not a claim of first release date or store publication**.
- **Defects**: explicit cross-linked GitHub issues where identified, otherwise master register only. `#12` light-mode defect is related to, but not the same requirement as, MX-QA-012 HTML readability.

## Gaps and Definition-of-Done requirements

1. **HLD and LLD approvals:** Per-feature HLD/LLD approval IDs, review decisions, design changes and diagrams still need authorised engineering sign-off. This catalogue establishes starter design records, not retrospective approvals.
2. **Fine-grained QA:** Store each executable test case, run/cycle ID, environment, device, actual result, screenshot/log, defect, retest, tester and approval. The register is currently strong on group acceptance but thin on individual case evidence.
3. **Live integrations:** OAuth device retest (MX-QA-030), Google/iCloud contacts UAT (draft PR #27), live AI HTTPS gateway + device UAT (PR #30) and future Odoo integration require separate validations.
4. **Release closure:** Each production release must link immutable commit/tag, production signing and SHA256, deployment/publishing evidence, install/upgrade proof, rollback reference and post-release smoke results.
5. **Odoo AI-036:** Verify draft-only creation, dedupe, vendor/account/tax mapping, source attachment/link, company isolation and deliberate manual posting/payment. Test that malicious invoice body cannot trigger post/pay.
